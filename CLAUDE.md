# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`next-level-editor` is a Vue 3 WYSIWYG rich-text editor distributed as an npm library. It is built on native `contenteditable` + `document.execCommand`, not on a document-model framework like ProseMirror/Tiptap. The build ships ES + UMD bundles with `vue` as an external peer dependency.

## Commands

```bash
npm run dev              # Vite dev server for the demo app (index.html -> src/demo/main.ts) at :5173
npm run build            # Build the library to dist/ (types auto-generated by vite-plugin-dts)
npm run build:demo       # Build the demo app (uses vite.demo.config.ts)

npm test                 # Vitest in watch mode (happy-dom)
npm test -- --run        # Vitest single run (what CI runs)
npm test -- --run src/utils/__tests__/formatting.test.ts   # Run one test file
npm test -- --run -t "toggles bold"                        # Run tests matching a name
npm run test:coverage -- --run   # Coverage (v8); thresholds: 70% lines/functions/statements, 65% branches
npm run test:ui          # Vitest UI

npm run test:e2e         # Playwright e2e (auto-starts dev server; chromium + mobile-safari)
npm run test:e2e:ui      # Playwright UI mode
npm run test:e2e:headed  # Headed
npm run test:e2e:debug   # Step debugger

npm run lint             # ESLint with --fix over .vue/.ts/.js
npx vue-tsc --noEmit     # Type check (run separately; lint does NOT type-check)
```

CI (`.github/workflows/ci.yml`) runs, as separate jobs: unit tests, `lint` + `vue-tsc --noEmit`, Playwright e2e, and `build`. Match all of these locally before assuming work is done — `npm run lint` alone is not sufficient because type errors are only caught by `vue-tsc`.

## Architecture

### Composable-orchestrator pattern

`src/components/NextLevelEditor.vue` is the single public component and the **orchestrator**. It owns almost no logic of its own — instead it wires together ~40 composables from `src/composables/` and passes their reactive state/handlers down as props/events to presentational child components (toolbar, panels, modals, menus). When adding a feature, the near-universal pattern is:

1. Put the logic in a `use*` composable in `src/composables/` (pure functions/DOM ops live in `src/utils/`).
2. Call it in `NextLevelEditor.vue`'s `<script setup>` and thread its outputs into the relevant child component.
3. Presentational components (`EditorToolbar`, `ModalsContainer`, `EditorPanels`, etc.) stay dumb — props in, events out.

`ModalsContainer.vue` centralizes every modal; `useModals` holds the show/hide flags. Toolbar structure is data-driven from `src/config/toolbarConfig.ts` + `useToolbarItems`.

### Layered structure

- `src/composables/` — reactive stateful logic (editing, history, selection, modals, export, comments, variables, accessibility, mobile, plugins). This is where most work happens.
- `src/utils/` — framework-agnostic pure helpers and DOM operations (`formatting`, `commands`, `export`, `templates`, `spellChecker`, `embed`, `pageManagement`, `fileManager`). Prefer extracting testable logic here.
- `src/components/` — Vue components; only `NextLevelEditor.vue` is public API, the rest are internal presentational pieces.
- `src/types/` — shared TS types, notably `plugin.ts` (the plugin/toolbar/command/slash-command contracts).
- `src/config/` — declarative config (toolbar layout).
- `src/styles/` — CSS is split into design tokens (`tokens.css`, `*-variables.css`), feature styles, and cross-browser fallbacks (`gap-fallback.css`, `focus-indicators.css`, `touch-targets.css`). `cssCodeSplit` is off, so all CSS ships as one `dist/next-level-editor.css` (exposed to consumers via the `next-level-editor/style.css` subpath export).
- `src/demo/` — the local playground app (App.vue, FeatureShowcase, example plugins/templates). Excluded from the library build and from coverage.

### Public API surface

`src/index.ts` is the library entry. It exports the `NextLevelEditor` component, a Vue plugin (`app.use(...)` default export), plus a curated set of composables (`useAccessibility`, `useComments`, `useVariables`, `useWritingAssistant`, `useSmartAutocomplete`, mobile helpers), companion components, util functions, and their types. **Anything meant to be consumable externally must be re-exported here.** Public `.d.ts` types are **auto-generated from source** by `vue-tsc -p tsconfig.build.json` during `npm run build` (`vite build && vue-tsc -p tsconfig.build.json`) — there is no hand-maintained declaration file, so exports and their types can't drift. (vite-plugin-dts was deliberately avoided: its `.vue`→virtual-`.ts` transform trips `TS4082` on `NextLevelEditor.vue`.)

The component is `v-model`-driven (`modelValue: string` of HTML). Feature-flag props gate the heavier subsystems: `showWritingStats`, `enableComments`, `enableVariables`.

### Security-sensitive: HTML sanitization

Because the editor round-trips raw HTML (paste, import, `v-model`, view-HTML editing), `src/composables/useHtmlSanitizer.ts` maintains explicit allowlists (`ALLOWED_TAGS`, per-element allowed attributes, unwrap tags). `dompurify` is also a dependency. Treat any change touching HTML ingestion, paste handling, or the sanitizer as security-relevant — do not widen the allowlists casually.

### Plugin system

`src/types/plugin.ts` + `usePlugin` define an extension contract: plugins register toolbar buttons, editor commands, and slash commands, and receive a `PluginContext` (content get/set, `execCommand`, selection, event bus). See `src/demo/examples/example-plugin.ts` for a worked example.

## Conventions

- Tests are colocated in `__tests__/` folders next to the code (`*.test.ts`, some `*.spec.ts`). Unit tests use Vitest + happy-dom with globals enabled; e2e specs live in `e2e/` and are excluded from Vitest.
- Path alias `@` -> `src/` is configured for Vitest (`vitest.config.ts`); source code itself uses relative imports.
- TypeScript is strict, with `noUnusedLocals`/`noUnusedParameters` on — unused symbols fail type-check.
- The build targets `es2015` and PostCSS/Autoprefixer targets a broad browser matrix (see `.browserslistrc`, `vite.config.ts`); cross-browser compatibility is a maintained concern (see the `CROSS_BROWSER_*.md` reports). Avoid APIs that don't downlevel cleanly.
